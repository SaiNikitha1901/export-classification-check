# Design decisions (platform: Member 1)

## A4: asynchronous runs, polling first, callback optional

A run takes tens of seconds (several LLM calls plus retrieval loops). Holding an HTTP request open that long ties up connections, breaks behind proxies with 30–60 s idle timeouts, and loses the answer if the client disconnects. So `POST /runs` returns **202 with a `run_id` immediately**, and the work happens in a worker behind a **Redis/RQ queue**.

**Polling (`GET /runs/{id}`) is the main method**, because:
- it works for every client (browser, CLI, eval runner, Locust), including clients behind NAT/firewalls that cannot receive inbound calls;
- it is idempotent and stateless, so a client that crashes can resume by `run_id`;
- reliability is simple: the state lives in Postgres, and any API replica can answer.

**Callbacks** (`callback_url`) are supported as a bonus: the API's housekeeping loop POSTs the final result, retrying up to 5 times with exponential backoff (2, 4, 8, 16 s). Callbacks need the receiver to be reachable and, in production, authenticated (signed payloads) and allow-listed to prevent SSRF. Those are reasons not to make them the default.

**Queue in between (A4):** RQ on Redis. The API enqueues by string name `agent_worker.tasks.run_classification` with `job_timeout = RUN_TIMEOUT_S`. The API never imports agent code, which keeps the boundaries clean.

**Watchdog:** a run whose job has died, timed out or disappeared is marked `failed` after `RUN_TIMEOUT_S + 30 s`. A client is never left polling forever, and a run that did not complete is never shown as an answer (A5). Runs still legitimately waiting in a long queue are left alone, because the watchdog checks the RQ job status first.

## D1/F2: validation at the boundary, quarantine

- One shared Pydantic model (`shared/contracts/request.py`) covers schema, type, range, category (country list, unit enum) and cross-field rules (material shares sum to 100 ± 1, unique materials, quantity ⇔ unit, declared HS code inside chapters 73/96). Unknown fields are rejected.
- Validation runs **before** any run row or job exists. A rejection is stored in `quarantine` with field-level errors (`field, error, value`) and returned as 422 with a `quarantine_id`. Integration tests check that the run count and queue length do not change.
- Invalid JSON is quarantined too (the raw body is kept, truncated).
- Cross-field rules run only once every field is valid on its own. That is how Pydantic works, and it keeps messages clear.

## D7: rate limiting is cost control

A multi-step agent makes several LLM calls per run. One client looping can exhaust a free-tier quota or a paid budget in minutes. Each client (`X-Client-Id`, else IP) gets `RATE_LIMIT_PER_MIN` submissions per **sliding** 60 s window (Redis sorted set). Over the limit returns **429 + `Retry-After`**. Rejected attempts are not counted, so a client that backs off recovers. Malformed requests count too, so a client cannot spam the validator.

## D7: whole-run cache

- **Key** = sha256 of the normalised request (lower-case, whitespace collapsed, materials sorted) + `PROMPT_VERSION` + the retriever's index `built_at`. Changing the prompt or rebuilding the index gives a new key, so stale answers are never served.
- Only `completed` runs are cached, never `escalated`/`degraded`/`failed`. A cached answer creates a new run row with `cache_hit = true` and `cached_from = <original run>`, with token cost 0. Lineage and feedback still work per run.
- If the retriever reports no index (`built_at` missing), caching is off.
- The effect on p95 and cost per run is measured in `loadtest/RESULTS.md` (`CACHE_MODE=repeat` vs `unique`).

## Observability choices

- JSON logs on stdout with `run_id` and `correlation_id` on every line (`shared/ecs_common`).
- `X-Correlation-ID` is accepted or generated by the API, echoed in the response, stored on the run, and passed to the worker.
- OpenTelemetry → Jaeger. The API stores the submit span's W3C `traceparent` in `runs.trace_context`, so the worker can continue the same trace (see `docs/contract_changes.md`).
- Per-container CPU/memory/uptime come from `ops/docker_exporter` (Docker Engine API), because cAdvisor cannot see containers on Docker Desktop (incident 2).
- Dashboards are generated by `ops/grafana/build_dashboards.py` and provisioned, so a clean clone shows them.
